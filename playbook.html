Superpowers subagent playbook

Superpowers is an open-source skills plugin for coding agents, from Jesse Vincent and Prime Radiant. Its subagent-driven-development skill runs a plan one task at a time: a new implementer, an independent review, then the next task. This guide shows how to set it up so that loop does good work.

Written from the skill files in Superpowers v7.0.1 (21 Oct 2026). Superpowers isn't made by Anthropic, and its skills change often.

The best way to use it

Spend your attention on the spec and the plan, choose Subagent-driven, set a model for each role, and let it run without check-ins. Then read the list of decisions it made for you before you merge.

The path from idea to merge

Skills are meant to trigger on their own, in this order. You make decisions at a few points, and the rest runs by itself.

  1. 1
    brainstorming
    YouAnswer its questions, choose an approach, and approve the design.
    You getA design doc in docs/superpowers/specs/. Nothing gets built before you approve it.
  2. 2
    writing-plans
    YouRead the plan, then choose Subagent-driven or Native.
    You getA task-by-task plan in docs/superpowers/plans/, with a recommendation on how to run it.
  3. 3
    using-git-worktrees
    YouUsually nothing. If the existing tests fail, decide whether to continue.
    You getAn isolated branch with a known test baseline.
  4. 4
    subagent-driven-development
    YouLeave it running. It stops only for the four reasons listed under While it runs.
    You getA conflict scan of the plan, then each task implemented and reviewed, tracked in a ledger file.
  5. 5
    Final whole-branch review
    YouRead the "Rulings I made" list when it finishes.
    You getA review on the most capable model, one fix wave, and every decision taken on your behalf.
  6. 6
    finishing-a-development-branch
    YouChoose to merge, open a pull request, or keep the branch.
    You getA full test run before the choice, and worktree cleanup after a merge.

Implementers also follow test-driven-development when a task calls for it, and verification-before-completion requires fresh evidence before anyone claims a pass. The README lists the worktree before planning, while the plan skill says to create it at execution time, so I've followed the skill.

Write a plan the loop can succeed with

An implementer sees only its own task, so gaps in the plan become guesses in the code. Most of your leverage is here, before any subagent starts.

Keep the spec linked

The spec outranks the plan when they conflict. Without one, the controller's decisions are only provisional.

Copy exact values into Global Constraints

Version floors, naming rules and limits go here word for word. Every task inherits them, and they tell the reviewer what to look for.

Size tasks by what a reviewer can judge

A task is the smallest piece with its own test cycle. Split only where a reviewer could reject one part and approve its neighbour, and fold setup and docs into the task that needs them.

Fill in every Interfaces block

Each task lists what it consumes and produces, with exact names and types. That's how an implementer learns what neighbouring tasks use.

Decide things, then stop

"Handle edge cases" decides nothing, and full function bodies turn the plan into the code. Give file paths, signatures, test assertions and spec values.

Use Review Focus

List the five inputs or failures your spec implies but no test covers, and attach a test for each to the task that owns that code.

Batch small repeated edits

If several tasks are the same small change across files, send them to one subagent and review the diff as a single unit.

Read the plan yourself

Check it the way you'd check a brief for a new contractor. This is your last cheap chance to change direction.

My advice

While it runs

The skill is built not to pause between tasks. Conflicts and gaps get a recorded ruling so work keeps moving. It stops and asks you for only four things:

  • An irreversible or destructive operation
  • A security-sensitive action
  • A side effect outside the worktree that normally needs asking, such as a merge, a push to a shared branch, or a publish
  • A plan so broken that every way forward is a guess

Match the model to the job

Name a model on every dispatch, because an omitted one inherits your session's, often the most expensive. The cheapest models can take two to three times the turns on multi-step work, so they don't always cost less.

RoleTier
Implementer, plan contains the complete code, or a single-file mechanical fixCheapest
Implementer working from prose, multi-file work, or debuggingMid-tier
Implementer needing design judgment or broad codebase knowledgeMost capable
Task reviewerMid-tier at least, higher for risky diffs
Scoped re-review of a small fixCheap to mid-tier

Trust the ledger after an interruption

Conversation memory doesn't survive compaction, but the ledger and git log do. Tasks marked complete aren't run again.

Know how the fix loop ends

A task gets five fix rounds. The first three resume the same implementer, and the last two use a fresh one on a stronger model. After that, the controller rules on what's left.

Read "Rulings I made" before merging

It's the only place the decisions made for you reach you, each with what it costs if wrong. Rework anything you disagree with.

Save money on long plans in Claude Code

The controller is the most expensive seat. If you ask, it can hand the whole plan to one mid-tier orchestrator subagent. Use this for whole plans only.

Parallel work has a specific place here. dispatching-parallel-agents is for separate problems with no shared state. Implementers in the subagent loop always run one at a time, because parallel ones conflict.

Mistakes that cost the most

MistakeWhat goes wrongDo this instead
Skipping the ledgerControllers that lost their place re-ran whole finished task sequences, the most expensive failure the skill reports.Keep the ledger, and trust it over memory.
One fixer per final-review findingEach rebuilds context and reruns tests. One real fix wave cost more than all its tasks together.Send one fixer the complete list.
Pasting history into dispatchesOne real dispatch reached 42k characters, 99% of it old history.Pass the brief as a file, plus only the interfaces it needs.
Running implementers in parallelTheir changes conflict.Run one at a time.
The controller fixing code itselfIt fills the controller's context, and the fix skips review.Resume the implementer.
Using HEAD~1 as the review baseThe reviewer misses all but the last commit of a multi-commit task.Record BASE before dispatching.
Letting subagents spawn reviewersYou pay for a duplicate review that counts for nothing.Only the controller dispatches reviews.
Dropping a finding silentlyThe problem disappears from view but stays in the code.Fix it, or park it with a recorded ruling at the round cap.
Running git clean -fdxIt deletes the git-ignored workspace and ledger.Avoid it mid-run. If it happens, recover from git log.
